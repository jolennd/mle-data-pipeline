# ADR 18: Containerize the pipeline (supersedes ADR 8)
Status: accepted
Context: ADR 8 skipped phase 6a because the brief had no container. The pipeline now needs to run the same way on any machine. This is a pipeline project: it runs a batch and exits, so there is no API, no port and no health endpoint.
Decision: Run phase 6a for kind pipeline. One image runs the batch as a non-root user, with a locked non-dev install. A run file has three services: the orchestrator server (UI), `flow` (all months through the orchestrator) and `pipeline` (plain entry point, one month). Data (downloads, database, results) lives in a named volume, not a bind mount, so an open notebook cannot lock the database. Settings (paths, months, database address) go in the run file's environment block because they are not secrets; a real secret would go in a git-ignored env file. The old API image, its ignore file and the make targets serve, docker-build and docker-test are replaced.
Consequences: Never run `flow` and `pipeline` at the same time (one writer). Results are read through a container (`make docker-results`). `make docker-down` keeps the data, `make docker-clean` deletes it and asks first. Phase 6b (deploy) stays skipped by ADR 9.
